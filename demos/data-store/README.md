# Data store demo

The catalog's PostgreSQL store, running for real: the full schema from
[`docs/data-store/`](../../docs/data-store/), loaded with the same worked graph
as the [ownership demo](../service-catalog-ownership/) (five people, five
identity groups, three teams, two systems, three components, six pieces of
infrastructure). Every fact in the seed arrives through `catalog.ingest` from
the source that owns it.

**[Open the schema page](./index.html)** (`index.html`, in a browser, no setup)
and its companion **[How it works](./flows.html)** (`flows.html`): four
worked scenarios (define a kind, create an instance, apply permissions,
move ownership) showing each call, the functions and tables it touches, and
the rows it writes. On the local environment, `./demo.sh pages` also serves both
(with the demos landing page) at https://catalog-data-store.dev.test.

The schema page is a visual guide to every table, view and function: what
writes each one, where every column's value comes from (an external source,
git config, or generated by the store), and the logic behind it, with a
guided tour.

Running the database itself:

Needs `kubectl`, `python3` and the local kind environment (`localenv`). The
database lives on its shared PostgreSQL: `.localenv.yaml` asks for database
`catalog_data_store` and the four roles the schema separates privileges with
(`databaseRoles`), and `localenv apps apply` (run by `./demo.sh up`) creates
them with Secret `catalog-data-store-db`. Namespace `catalog-data-store` holds
a `psql` client pod that connects as the owner with verified TLS, and OpenFGA.

Without the local environment, `CATALOG_PG=standalone ./demo.sh up` runs its
own Postgres (`standalone.yaml`) and creates the same database, roles and
Secret. CI uses that mode.

```
./demo.sh up            # localenv apps apply, deploy k8s.yaml, recreate the schemas, load sql/*.sql
./demo.sh walkthrough   # the guided tour: 11 steps, prints SQL and results
./demo.sh test          # invariant checks (rolled back), then check-page
./demo.sh check-page    # does index.html match the live schema?
./demo.sh drift         # do OpenFGA and the SQL rule agree? (--apply repairs)
./demo.sh pages         # serve the demo pages at https://catalog-data-store.dev.test
./demo.sh psql          # explore by hand
./demo.sh down          # remove the workloads (the database stays; `localenv apps delete catalog-data-store` drops it)
```

The walkthrough changes data, so run it on a fresh database. `./demo.sh up`
always starts from the seed. The [tutorial](../../docs/data-store/tutorial.md)
covers the same steps with commentary.

## Trying things by hand

```sql
-- be the catalog service, acting for Carol (Search)
set role catalog_data_store_api;
set catalog.viewer = 'user:carol';
select ref, effective_owners, redacted from api.resource order by ref;
select * from api.who_owns('component:cart-service');
select jsonb_pretty(api.context(array['component:checkout-service'], 1));

-- back to the owner to see the facts underneath
reset role;
select * from authz.access_matrix('component:checkout-service');
table authz.fga_tuples;
```

For a GUI client, `localenv apps describe catalog-data-store` lists the Secret
holding the connection details (the database only accepts TLS).

## Keeping the schema page current

`index.html` must describe exactly the schema in `sql/`. This is a
requirement, not a nicety: when a change adds, removes, renames or retypes a
table, view, column or function, update in the same change:

1. the `schema-data` JSON block in `index.html`:
   - **`tables`**: the object, its columns with the exact type Postgres
     reports (`timestamp with time zone`, `text[]`, enum names), keys, and its
     `purpose`, `rules`, `indexes`, `writtenBy` and `readBy`;
   - **each column's `origin` and `by`**: where its value comes from
     (`external`: sent by a source or a user edit; `config`: defined in git;
     `generated`: set by the store's functions, triggers or defaults;
     `derived`: a rebuilt cache; `computed`: a view) and what sets it;
   - **`functions`**: the signature, what it does, and the tables it touches;
   - **`edges`**: foreign keys and derivations it adds or removes;
   - **`tour`**: any step whose explanation the change affects;
2. [`docs/data-store/reference.md`](../../docs/data-store/reference.md);
3. `flows.html`, if the change alters a flow it walks through (defining a
   kind, ingesting an instance, permissions, ownership propagation). Its
   example rows were captured by running those scenarios against the seed;
   re-run them and update the `flow-data` block.

`./demo.sh check-page` (also run by `./demo.sh test`) compares every table,
view, column type and function in the database with the page, and fails with
a diff while they disagree. It also fails if the page refers to an object that
doesn't exist, if a column has no valid `origin` and `by`, or if `flows.html`
names a table, view or function that isn't on the schema page. It can't see a logic change that leaves the shape alone, such
as a new rule inside a function body, so for those, update the page's text by
hand.
